**翻墙机场分流，就是让不同请求走不同路径：需要代理的服务交给机场节点，适合直连的网站和局域网设备保留直连。** 如果你开了机场后国内网站反而变慢、套餐流量消耗异常，或浏览器能用而其他应用不能用，应先检查分流与流量接管，再判断线路是否需要更换。

对希望国内服务直连、指定海外服务走代理的读者，可以先从兼容客户端的**规则模式**开始。全局模式适合短时对照排查；是否开启 TUN，则取决于需要接管哪些应用。理解这两个设置层次，比反复换节点更容易找到原因。

如果你还没有订阅，可先收藏本站的 **[2026年翻墙机场推荐评测｜稳定便宜VPN机场排行榜（高性价比科学上网工具长期更新）](/vpn-recommend/)**，比较设备兼容、套餐与测试条件，再用本文的分流验收表验证候选。已有订阅的读者，可以直接从下面的症状表开始。

本文提供原理说明和可自行执行的检查流程，不把示例当作机场实测。技术依据为文中链接的官方文档，核对日期为 **2026年11月13日**；作者信息见[关于 YouYou](/about/)，推荐内容的依据与推广关系见[评测方法](/methodology/)和[广告披露](/disclosure/)。

## 一、先按症状定位：该改分流，还是检查机场？

| 你遇到的情况 | 先核对什么 | 下一步怎么做 |
|---|---|---|
| 开机场后国内网页、网盘或下载变慢 | 这些请求是否被送到海外节点 | 查连接记录、命中规则与策略组 |
| 没怎么用海外服务，机场流量却掉得快 | 国内视频、系统更新、云盘是否走了代理 | 对照应用用量、节点倍率与后台扣量 |
| 同一节点全局模式能用，规则模式不能用 | 规则是否直连、拦截或选到了另一节点 | 固定节点，检查目标请求的实际路径 |
| 浏览器能用，桌面应用不能用 | 应用是否遵循系统代理 | 查看接管范围，再按需测试 TUN |
| 开启 TUN 后打印机、NAS或路由器页面异常 | 局域网地址是否被错误处理 | 核对局域网排除、直连规则和系统路由 |
| 规则与出口正确，多个常用节点仍持续卡顿 | 本地接入、机场线路和目标服务状态 | 做晚高峰与另一接入网络的对照测试 |

这张表用于缩小排查范围。同一个症状可能有多个原因，例如 DNS 异常与错误分流都可能表现为网页打不开，不能只凭一次成功或失败判断服务质量。

## 二、基础概念：机场、客户端和分流分别负责什么？

“翻墙机场”“VPN机场”“机场VPN”通常是用户对节点订阅服务的不同叫法。它们不是统一的质量认证，也不能说明客户端已经正确配置。

| 名称 | 在一次访问中负责什么 | 你需要确认什么 |
|---|---|---|
| 机场服务商 | 提供账号、套餐、节点和订阅 | 套餐有效、服务与设备兼容 |
| 订阅 | 同步节点，有些订阅也带策略组和规则 | 导入的是节点列表，还是完整配置 |
| 客户端 | 在本地接收请求、执行规则并建立连接 | 当前启用的是哪份配置 |
| 节点 | 承担选定的代理连接 | 节点可用，协议和目标用途兼容 |
| 规则 | 决定某个请求交给谁处理 | 匹配条件、顺序与处理动作 |
| 策略组 | 在节点或其他策略之间作选择 | 组内最终选中了哪个节点或直连动作 |
| DNS | 把域名解析为地址 | 使用哪条解析路径，是否与配置配合 |

例如，你可能在“节点选择”组里选了日本节点，但视频服务命中的是另一个“流媒体”组，最终仍走香港节点。**只看首页选中了哪个节点，不能确定每一个应用的实际出口。**

刚接触这些术语，可先读[翻墙机场、节点、订阅与客户端基础教程](/article/what-is-vpn-airport-beginner-guide-2026/)；已经拿到订阅但不会导入，可接着看[Clash与Shadowrocket订阅导入教程](/article/airport-subscription-clash-shadowrocket-guide-2026/)。

## 三、工作原理：先接管请求，再决定走哪条路

一次典型的处理过程可以这样理解：

> 应用发出请求 → 系统代理或TUN等方式把请求交给客户端 → 客户端执行当前模式与规则 → 策略组选择出口 → 直连目标或经过机场节点。

这里有两类独立设置：

- **接管方式**解决“哪些请求进入客户端”，例如系统代理、应用内代理、TUN。
- **处理策略**解决“进入客户端以后怎么走”，例如规则、全局、直连模式。

### 系统代理和TUN有什么区别？

| 接管方式 | 主要作用 | 使用时的边界 |
|---|---|---|
| 系统代理 | 由遵循系统代理设置的应用把请求交给本地代理端口 | 部分应用使用独立设置，可能不遵循系统代理 |
| 应用内代理 | 在某个应用中单独指定HTTP或SOCKS等代理 | 只影响该应用所支持并交给代理的连接 |
| TUN | 通过虚拟网络接口和路由接管更广范围的IP流量 | 实际覆盖受系统、路由、排除项、IPv6和客户端实现影响 |

Mihomo 的[TUN官方文档](https://wiki.metacubex.one/config/inbound/tun/)把自动路由、排除网段、接口和应用范围分别列为配置项。因此，**开启 TUN 不等于所有请求一定经过机场节点**：被接管的请求仍可能按规则直连，也可能存在未被接管的范围。

同样，“全局模式”只处理已经进入代理内核的请求。某个应用没有进入客户端时，切换全局模式也不能自动解决接管问题。

### 规则、全局、直连怎么选？

Mihomo 的[运行模式说明](https://wiki.metacubex.one/config/general/#运行模式)将其区分为 `rule`、`global`、`direct`。下面以使用 Mihomo 内核的 Clash 类客户端为主要示例；其他客户端的名称与实现应按各自说明核对。

| 模式 | 对进入内核的请求如何处理 | 适合什么时候使用 |
|---|---|---|
| 规则 / Rule | 按配置规则交给直连、代理策略组或拦截动作 | 日常需要区分不同服务路径时 |
| 全局 / Global | 交给全局策略组当前选择的代理或策略 | 短时判断问题是否与规则选择有关 |
| 直连 / Direct | 使用直连策略访问目标 | 检查本地连接基线，或暂时不使用代理出口时 |

全局策略组里还要确认实际选择，不能只看“Global”字样就认定已经使用某个海外节点。`DIRECT` 也不等于退出客户端；请求仍可能经过客户端的接收、解析等处理。

如果你使用 Shadowrocket，可参照同样的“接管、规则、策略、出口”思路核验，但不要把 Mihomo 的 YAML 配置或模式名称直接套过去。

## 四、照着做：用连接记录完成一次分流设置

以下流程适用于已导入兼容订阅的读者。各客户端入口名称可能不同，以当前版本中的配置、规则、策略组、连接或日志页面为准。

### 第1步：备份当前配置，固定测试条件

保存当前配置、订阅来源和关键开关状态。记录正在使用的客户端、设备、网络、节点和模式，暂时暂停大文件下载与云盘同步，避免后台流量干扰判断。

完整订阅链接可能包含账号令牌，应按凭证保管。截图或向客服提交材料时隐藏令牌、密码和个人信息；不要把完整配置上传到不明转换网站。

### 第2步：确认当前配置确实包含分流规则

“导入成功”可能只是导入了节点。检查当前启用的配置是否还有规则与策略组，规则集是否下载成功，以及组名是否对应现有节点。

如果服务方提供多种订阅格式，应使用与客户端兼容的格式。先保留一份可工作的基础配置，再添加自己的需求，避免同时叠加多份来源不明的规则。

### 第3步：选择规则模式，核对策略组实际选择

先启用规则模式，选择一个便于复测的可用节点。检查常用的网页、视频或其他业务组，确认它们使用这个节点、引用正确的组，或者按你的意图直连。

自动选择、故障转移等组可能改变实际节点。排查单个问题时，可以在客户端支持的范围内临时固定选择，并记录最终节点，减少变量。

### 第4步：发起新请求，在连接页面找证据

打开一个你希望直连的国内网站，再打开一个你希望经代理访问的目标服务。按域名、应用进程或时间查找对应连接，记录：

- **目标**：是哪一个域名或地址；
- **匹配**：命中了哪条规则或规则集；
- **策略**：交给了哪个策略组；
- **结果**：最终是 `DIRECT`、具体节点，还是拦截；
- **体验**：页面、登录、图片或视频是否完成。

下面仅示范记录方法，**不是实际机场测试结果**：

| 测试对象 | 期望路径 | 连接记录中的模拟结果 | 应如何判断 |
|---|---|---|---|
| 国内服务A | 直连 | 兜底规则 → 默认代理组 → 日本节点 | 与期望不符，查规则和顺序 |
| 海外服务B | 指定代理 | 业务规则 → 业务组 → 所选日本节点 | 路径符合期望，再测实际功能 |
| 本地NAS地址 | 本地网络 | 局域网规则 → DIRECT | 继续验证文件访问或管理页面 |

一个页面可能调用登录、图片、接口和视频等多个域名。如果首页能开但图片不显示，应检查失败的那条请求，而不是只看首页域名。

### 第5步：只修改与问题有关的规则

在支持本地规则或配置覆写的客户端中，为已确认需要调整的**具体域名、地址范围或应用**添加规则，并选择现有策略。新手优先从范围较小的域名规则开始，避免一条宽泛规则改变大量业务。

Mihomo 的[路由规则文档](https://wiki.metacubex.one/config/rules/#优先级)说明了自上而下的匹配顺序；`MATCH` 用于匹配所有请求。实际设置时，应检查具体例外是否位于更宽泛的规则之前，兜底规则是否放在后面。代理能力和规则附加条件也可能影响匹配行为。

比如，一个明确应直连的服务如果先被宽泛的代理规则匹配，在末尾追加直连例外可能无法达到目的。先看命中记录，再改顺序，比不断往列表底部添加规则有效。

### 第6步：建立新连接，再验证订阅更新后是否保留

保存并重新加载配置后，关闭测试页面或重新启动相关应用，发起新连接。已有长连接可能继续使用原路径，不能只刷新一次就判断修改失败。

订阅更新是否覆盖本地修改，取决于客户端的配置保存与合并机制。优先使用该客户端明确支持的本地覆写方式；更新订阅后，再核对自定义规则、策略组和出口。若出现问题，恢复备份后重新定位。

## 五、国内网站变慢、机场流量异常，怎样判断原因？

### 情况1：国内业务确实走了代理

先比较同一设备、同一网络上的实际任务：关闭代理接管后的正常基线、规则模式中的期望直连，以及误走代理时的表现。测试时记录时间和路径，不要同时换网络与节点。

若连接记录确认国内大流量业务经过机场，改为符合需求的直连后，该部分流量通常不再通过机场节点。是否变快，仍受本地宽带、目标服务器与网络状态影响。

**流量计算示例：**假设某个月有 30GB 国内业务和 20GB 需要代理的业务，这些数值均按同一计费传输口径统计，代理节点均为 2 倍倍率。为说明计算，暂不计额外开销：

| 路径安排 | 通过机场的传输量 | 按2倍倍率估算的扣量 |
|---|---|---|
| 两类业务都走机场 | 50GB | 100GB |
| 国内业务直连，仅指定业务走机场 | 20GB | 40GB |

这是有明确假设的算例，不能推算成每个人都能节省固定比例。实际扣量还要核对上下行统计、倍率、后台延迟及套餐规则，详细方法见[机场流量倍率与套餐计算教程](/article/airport-traffic-multiplier-guide-2026/)。

### 情况2：路径正确，后台仍在持续扣量

暂停其他设备上的代理业务，对照本地连接用量与服务商后台记录，检查后台更新、离线缓存、云盘上传和其他在线设备。

如果出现无法解释的持续流量或陌生使用记录，再按[机场订阅链接安全指南](/article/airport-subscription-security-guide-2026/)核对泄露与令牌重置。不要仅凭某一天流量变多，就认定是规则错误或账号被盗。

### 情况3：国内服务显示直连，仍然慢

检查该服务的其他域名、DNS解析、系统路由与本地接入。必要时对照关闭接管后的表现，确认是不是只有某一份配置启用时异常。

如果关闭客户端后也慢，或换到手机热点后明显不同，应继续检查本地网络。可参考[电信、联通、移动机场适配与对照测试教程](/article/vpn-airport-telecom-unicom-mobile-guide-2026/)，避免把接入网络问题全部归因于机场。

## 六、DNS、IPv6和IP检测，为什么要分开看？

### DNS解析路径不等于业务出口

DNS负责查询地址，后续业务连接负责传输内容，两者需要分别核对。Mihomo 的[DNS配置文档](https://wiki.metacubex.one/config/dns/)列出了独立的解析模式、IPv6响应、解析服务器策略和遵循路由规则等选项。因此，看到业务连接经过节点，仍应结合当前配置检查解析行为。

遇到“域名打不开，其他连接正常”时，先核对当前生效的DNS配置和失败记录。浏览器的安全DNS、系统私人DNS或其他应用内设置，也应纳入检查；不要一开始同时更换多组DNS、解析模式和路由规则。

### 一次IP检测，只能说明当次请求

IP检测页显示海外地址，只能证明访问这个检测服务时使用了相应出口，不能证明视频应用、聊天工具和所有后台服务都经过相同路径。

同理，检测页显示本地地址，也可能是该页面按规则直连。判断目标服务是否走代理，仍应查看它自己的连接记录；节点名称、IP地区识别与平台是否允许访问，也要分别确认。

### IPv4和IPv6要核对实际覆盖

设备、目标服务、客户端接管和节点对两种地址的处理可能不同。保留当前设置，先查看失败连接使用的地址类型，再按客户端说明检查对应的路由、解析和代理能力。

不要把“一律关闭IPv6”当作所有问题的固定答案。若确实需要临时调整进行对照，应记录原设置，并在测试后恢复或采用已验证的配置。需要进一步核对解析隐私时，可读[DNS泄露检测与排查教程](/article/dns-leak-2026/)。

## 七、出现问题时，按这个顺序排查

| 观察到的证据 | 优先检查 | 本次只改变什么 |
|---|---|---|
| 目标应用的新请求没有出现在连接记录中 | 当前接管方式、应用独立代理、记录筛选条件 | 核对该应用设置，或测试客户端支持的TUN接管 |
| 请求进入客户端，但命中DIRECT或拦截 | 规则条件、顺序和规则集是否生效 | 调整已确认有问题的一条规则 |
| 命中正确的组，最终节点却不对 | 组间引用、自动选择和业务专用组 | 固定相关组的选择 |
| 同节点全局可用，规则模式不可用 | 两种模式下实际策略、出口及相关DNS行为 | 保持节点不变，对照目标连接 |
| 同节点两种模式都失败 | 节点、DNS、本地网络或目标服务状态 | 先换一个已知可用节点对照 |
| 只有TUN开启时局域网服务异常 | 排除网段、直连策略、路由与其他网络软件 | 核对该局域网地址的处理路径 |
| 路径正确但晚间持续卡顿 | 本地接入、节点负载、机场线路和目标业务 | 固定任务，换时段或接入网络对照 |

系统代理与 TUN 同时开启，并不必然造成重复代理。如果遇到异常，应检查具体应用是否又设置了独立代理、请求实际经过哪条路径，以及客户端如何处理这些入口。

如果同时运行企业VPN、其他网络隧道或安全软件，要结合组织要求和各自路由配置排查。关键业务不宜通过随意覆盖路由来试错。

## 九、常见问题：翻墙机场分流设置FAQ

### 1. 翻墙机场日常用规则模式还是全局模式？

如果希望国内服务直连、指定海外服务走代理，可以从规则模式开始，并用连接记录确认实际路径。全局模式适合短时对照排查；它只影响进入代理内核的请求，不能保证所有应用都被接管。

### 2. 开启TUN就等于全局代理吗？

不等于。TUN主要负责通过虚拟网络接口和路由接管流量，规则、全局或直连负责决定接管后的处理方式。TUN下仍可以规则分流，实际覆盖还受路由、排除项、系统和IPv6设置影响。

### 3. 为什么开翻墙机场后国内网站变慢？

可能是国内请求误走海外节点，也可能涉及DNS、本地网络或目标服务。先查看慢请求的命中规则、策略组和最终路径，再与同一网络关闭接管时的表现对照，不要直接认定机场质量差。

### 4. 设置国内直连，能减少机场流量消耗吗？

原本经过机场的请求改为直连后，该部分通常不再通过机场节点。实际减少多少取决于业务量、节点倍率和计费规则；系统更新、云盘同步与其他在线设备也应一起核对。

### 5. 同一节点全局能用，规则模式不能用，应该换机场吗？

先检查目标请求是否被直连、拦截，或交给了另一个策略组和节点。保持网络、节点与目标不变，建立新连接后对照记录，并核对模式相关的DNS等设置，再决定是否需要更换服务。

### 6. IP检测显示海外地址，能证明所有应用都走机场吗？

不能。IP检测只反映访问该检测服务的当次请求，不同应用或域名可能命中不同规则。应查看目标服务自己的连接记录，分别核对接管、策略组、最终节点和实际功能。

### 7. 为什么更新机场订阅后，自定义分流失效了？

可能是本地修改被覆盖、规则顺序变化，或策略组名称不再对应。先比较更新前后的配置，再使用客户端明确支持的本地规则或覆写机制，并在更新后重新验收。

### 8. 新手怎样从翻墙机场推荐里找到适合自己的服务？

先按设备、预算、常用地区与任务筛选候选，再用兼容客户端核对规则、接管、出口、倍率和晚高峰表现。优先通过试用或短周期验证，不要把排行榜位置、专线标签或一次测速当作持续可用保证。
